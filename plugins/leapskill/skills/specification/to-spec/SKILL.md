# 转成技术规格

将已确定的对话上下文和代码库理解综合为明确的、可构建的技术规范，并具有最少的测试接缝和完整的用户故事。

---

## 核心不变量

1. **纯综合，零询问**：严格根据已建立的上下文和代码库事实进行综合；不要采访用户。
2. **最高层的最小接缝**：优先选择现有的高级测试接缝；切勿引入不必要的内部模拟接缝。
3. **详尽的用户故事**：生成一个全面的、编号的列表“作为一个<参与者>，我想要<功能>，以便<好处>”故事涵盖所有用户路径。
4. **针对具体片段的决策**：指定架构决策、接口和模式更改，而无需脆弱的硬编码代码片段（除非源自经过验证的原型）。
5. **严格的范围外划分**：明确列出范围外的功能，以防止范围蔓延和不受约束的工作。

```

```

|组件|责任|格式/模板|
|---|---|---|
| **问题与解决方案** |框架以用户为中心的意图|问题/解决方案陈述|

| **测试决定** |指定外部验证接缝|行为驱动测试策略|

## 分步程序 (TWI)

### 第 1 步：自主代码库和接缝检查
- **操作**：探索存储库以检查现有模块、域术语表术语和 ADR。
- **关键点**：确定最高可用的集成接缝以在外部测试该功能。
- **为什么**：通过高级接缝进行测试可以验证真实的系统行为，同时让内部实现细节可以自由重构。

### 第 2 步：制定全面的用户故事
- **行动**：起草一份详尽的、编号的用户故事列表，捕获所有主要和边缘情况的用户交互。
- **要点**：遵循严格的模板：`1. 作为 <actor>，我想要 <feature>，以便 <benefit>`。
- **为什么**：详细的用户故事会阻止实施者在编码期间做出临时的产品假设。
- **内嵌清单**：
  - [ ] 每个用户故事都有明确的参与者和切实的好处
  - [ ] 边缘案例和故障状态作为不同的故事进行介绍
  - [ ] 用户故事陈述中没有实施术语

### 步骤 3：正式确定实施和测试决策
- **操作**：记录模块边界、修改的接口、数据库模式更改和 API 契约。
- **要点**：省略易失性文件行号或推测性代码片段。
- **为什么**：脆弱的代码片段立即变得陈旧并误导下游实施代理。

### 步骤 4：定义范围外边界并发布
- **操作**：详细说明明确不包含的内容，应用“ready-for-agent”分类标签，并发布到配置的问题跟踪器或“.scratch/<feature-slug>/spec.md”。
- **要点**：如果问题跟踪器未配置，请指示用户运行“/setup-engineering-workflows”。
- **为什么**：明确的排除边界可防止范围膨胀并保持后续工单分解的范围。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“在编写规范之前，我会再问用户几个问题。”* | **编写规格期间不做访谈。** |如果需求仍然模糊，返回 `grill-me`。`to-spec` 只做纯综合。 |
| *“我将编写大量模拟重单元测试决策。”* | **在尽可能高的公共接缝处进行测试。** |大量模拟测试会在重构期间中断，并且无法验证实际的端到端功能。 |
| *“在规范中包含完整的实现代码块。”* | **指定接口和决策，而不是完整代码。** |规范中的实现代码使开发人员代理无法看到实时代码库的细微差别。 |
| *“跳过超出范围的部分，因为它看起来很明显。”* | **强制明确的超出范围部分。** |范围边界的模糊性会导致实施过程中范围蔓延失控。 |
