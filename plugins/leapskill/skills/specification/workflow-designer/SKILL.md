# 工作流设计器

通过识别循环操作循环、正确推送检查点以及定义明确的执行合同，设计并规范可重复的人机交互和自主工作流。

---

## 核心不变量

1. **将检查点向右推**：将人工检查点尽可能推迟到下游；在请求审查之前最大化自主工作。
2. **可操作的决策简报**：检查点必须提供一份紧凑的、可用于决策的简报，其中包含清晰的差异和链接，而不是原始的、未经策划的输出。
3. **不强制任何结构性**：仅在问题域严格要求时添加 AI 代理、时间表或批准门。
4. **自包含规范完整性**：只有当实施者代理可以在不询问澄清问题的情况下构建它时，工作流规范才是完整的。
5. **持久的注释分离**：区分不可变的工作流规范（`workflows/*.md`）和不断发展的领域观察（`NOTES.md`）。

```
[ Operational Habit / Team Routine ] ──► [ Loop Identification & Grilling ] ──► [ Workflow Formalization ] ──► [ Implementer Handoff ]
```

|组件|责任|地点 |
|---|---|---|
| **工作流规范** |可执行合约（触发、输入、操作、检查点）| `workflows/*.md` |
| **域和工具注释** |观察词汇、习惯、工具、渠道 | `NOTES.md` |
| **拷问协议** |需求和边界的苏格拉底式蒸馏| `skills/grilling/SKILL.md` |

## 分步程序 (TWI)

### 第 1 步：识别循环循环并记录基线注释
- **操作**：分析用户的重复任务（每日、每周、每次发布）并将观察到的工具/渠道记录到“NOTES.md”中。
- **关键点**：映射从触发到最终交付的自然生命周期。
- **为什么**：捕获当前基线可以防止设计与日常现实不匹配的理论工作流。

### 步骤 2：对工作流边界进行苏格拉底式拷问
- **行动**：进行一轮集中拷问探索：
- **触发器**：基于事件（例如 webhooks、新问题）与时间计划（例如 cron）。
- **输入和状态**：必须摄取哪些工件。
- **行动**：离散操作或代理转换。
- **检查点**：最小的审查门被推到了最后。
- **内嵌清单**：
  - [ ] 通过后备轮询间隔明确指定触发器
  - [ ] 检查点提供决策简报
  - [ ] 定义故障路径和升级负责人

### 步骤 3：编写可执行工作流规范
- **操作**：将工作流契约写入“workflows/<name>.md”，详细说明触发器、输入、操作、检查点概要和输出。
- **关键点**：确保实施者代理可以单独从文档实施脚本或自动化。
- **为什么**：工作流合同中的模糊性会导致严重的自动化失败。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“要求人工验证每个中间步骤。”* | **向右推检查站；批量人工评论。** |频繁的中断会导致人类疲劳并破坏自动化效率。 |
| *“转储人工检查点的原始日志文件。”* | **生成可供决策的综合摘要。** |人类查看干净的执行摘要的速度比原始调试日志快 10 倍。 |
| *“假设每个工作流步骤都需要LLM代理。”* | **尽可能使用确定性脚本；人工智能仅在需要判断的情况下使用。** |对于结构化操作，确定性脚本比 LLM 更快、更便宜、更可靠。 |
