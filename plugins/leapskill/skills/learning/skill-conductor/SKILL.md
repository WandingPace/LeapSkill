# 技能指挥

代理技能全生命周期管理：**草稿→测试→审核→改进→打包**。

一项管理技能创建和优化的主要学科，植根于 10 项规范创作原则。

---

## 核心不变量和 10 条规范创作原则

1. **飞行前检查**：在执行工作流之前，先确认依赖、环境和前置条件都已就绪。
2. **描述中没有流程**：描述定义触发边界（“在...时使用”、“不要用于...”），绝不是工作流配方。
3. **内容地图 (MOC)**：`SKILL.md` 是指向模块化参考的清晰架构地图（< 500 行）。
4. **新从业者同理心**：解释步骤背后的基本原理，以便代理理解上下文。
5. **行业内培训 (TWI)**：将关键说明构建为“行动”、“关键点”和“原因”。
6. **盲代理可测试性**：确保在没有先前对话历史记录的情况下执行指令时明确无误。
7. **内联风险检查表**：将验证检查表直接放置在高风险接缝处。
8. **每个概念一个术语**：始终使用一致的领域术语。
9. **零秘密/环境清洁**：切勿对凭据、token或绝对用户主路径进行硬编码。
10. **将形式与故障相匹配**：使用有针对性的结构约束和反合理化表来应对特定的故障模式。

## 核心生命周期模式

|模式|触发/背景 |关键输出|
|---|---|---|
| **1.创建** | “培养一项技能”、“...的新技能” |完整生命周期：意图→架构→脚手架→编写→评估|
| **2.改进** | “修复此技能”，“它不会触发”|诊断 → 评估循环 → 门控自更新 → 迭代 |
| **3.验证** | “测试此技能”、“运行评估”|结构检查+触发测试+BinEval评分 |
| **4.评论** | “审查这项技能”，质量审核| 11点质量门评估|
| **5.优化** | “改进触发”、“优化描述” |通过训练/测试分割进行自动描述优化 |
| **6。套餐** | “分发包” |验证 + 捆绑到发布工件 |

## 分步程序 (TWI)

### 第 1 步：捕捉意图并定义触发器
- **行动**：提取2-3个具体的用户场景并建立积极和消极的触发边界。
- **关键点**：指定用户所说的确切短语以及技能必须拒绝的相邻域。
- **为什么**：清晰的边界可防止触发不足和误报过度触发。

### 第 2 步：架构和渐进式披露
- **操作**：选择架构模式（顺序、迭代、上下文感知）和结构文件。
- **关键点**：保持 `SKILL.md` 简洁（< 500 行）并将大量模式或表格放入引用中。
- **为什么**：臃肿的指令文件会耗尽注意力预算并降低执行质量。

### 步骤 3：写 Frontmatter 和 Body
- **操作**：起草 YAML frontmatter，其中包含短横线命名和触发器丰富的描述，后面是 MOC、TWI 步骤和护栏。
- **内嵌清单**：
  - [ ] Frontmatter 名称与目录名称匹配
  - [ ] 描述为 $\le 1024$ 个字符，不包含任何流程步骤
  - [ ] 指定的负面触发器（“请勿用于...”）
  - [ ] 包括反合理化表
  - [ ] 没有硬编码的token、密码或特定于计算机的路径

### 步骤 4：使用 BinEval 5 Dimensions 进行验证
- **行动**：评估**发现、清晰度、结构、稳健性、完整性**。
- **要点**：在宣布发布准备就绪之前，通过每一个关键的关卡检查。
- **为什么**：多维评估在分配之前捕获隐藏的故障模式。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“在描述中添加步骤有助于模型。”* | **禁止：描述中的零进程。** |模型遵循描述步骤并跳过全面的正文说明。 |
| *“技能很小，所以不需要负面触发。”* | **描述中的强制性负面触发因素。** |如果没有负边界，技能就会在松散相关的查询上错误地触发。 |
| *“一个 1200 行的大 Markdown 文件更容易管理。”* | **逐步披露：SKILL.md < 500 行。** |超负荷的环境会分散注意力并导致跳过指令。 |
| *“如果Markdown看起来干净，我们可以跳过测试。”* | **触发对正面和负面测试用例的评估。** |干净的散文在实际的智能体路由中仍然可能失败。 |
