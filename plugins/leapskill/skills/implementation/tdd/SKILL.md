# 测试驱动开发 (TDD)

通过严格的红色 → 绿色 → 验证周期来实现强大、可维护的功能。通过公共接缝而不是私有实现细节来验证行为。

## 核心原则

> **首先编写失败的测试，见证它因正确的原因而失败，然后只编写使其绿色所需的最少代码。**

---

## 核心不变量

1. **严格的红色优先执行**：在看到自动化测试因预先商定的接缝而失败之前，切勿编写生产实现代码。
2. **行为测试优于实施检查**：测试必须断言可观察的输入/输出行为和公共契约，而不是私有变量或内部调用链。
3. **独立期望值**：断言必须与独立的基本事实（测试夹具、域规范、已知文字）进行比较，从不重新计算镜像逻辑。
4. **垂直 tracer-bullet 切片**：一次交付一个垂直切片（一个测试 → 最少代码 → 绿色），而不是预先批处理水平测试套件。
5. **确定性和隔离测试夹具**：测试必须在毫秒内执行，没有交叉测试状态泄漏、未播种的随机种子或未固定的时钟。

## 分步程序 (TWI)

### 第 1 步：识别并确认公共接缝
- **操作**：说明您打算测试的公共接口和可观察合约，并确认与领域约定的一致性。
- **关键点**：在公共边界锚定断言；不要进入内部私有状态。
- **为什么**：通过私有内部进行测试会产生脆弱的测试，这些测试会在无害的重构过程中中断。

### 第 2 步：编写失败测试（红色）
- **操作**：编写指定预期行为的单一集中测试并运行测试运行程序以观察失败。
- **关键点**：验证测试失败具体是因为新行为不存在，而不是由于语法或设置错误。
- **内嵌清单**：
  - [ ] 测试命名确切的业务能力（例如“returns_discounted_total_for_premium_member”）
  - [ ] 测试失败并出现预期的断言错误
  - [ ] 从独立领域常量导出的期望值
- **为什么**：不能相信未正确失败的测试可以防止回归。

### 步骤 3：实施最少代码（绿色）
- **行动**：编写最简单、最直接的代码，使失败的测试通过。
- **要点**：不要预期投机性要求或编写未执行的分支。
- **为什么**：最少的代码可以保持变更集的紧密性并防止未经验证的死逻辑。

### 第 4 步：验证套件和周期
- **行动**：运行完整的测试套件以保证零回归。
- **关键点**：在进行下一个垂直 tracer-bullet 切片之前，所有测试都必须为绿色。
- **为什么**：立即捕捉回归使调试成本接近于零。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“我将首先编写实现，然后添加测试。”* | **禁止：必须先编写测试并观察失败。** |在代码之后编写的测试往往会反映实现偏差并错过边缘情况故障。 |
| *“我可以模拟这个内部助手来测试私有方法。”* | **仅通过公共接缝进行测试。** |对私有内部结构的模拟让测试和实现过度耦合，隐藏真正的集成错误，也让架构难以重构并隐藏了真正的集成错误。 |
| *“在编写任何代码之前，我将编写所有 15 个测试用例。”* | **垂直 tracer-bullet 切片：一次进行一个测试。** |在真正的实现学习之前，批量测试会锁定不成熟的接口假设。 |
| *“测试在第一次运行时通过，没有任何变化。”* | **立即调查：同义反复或错误测试。** |无需更改实现即可通过的测试断言某些内容已经正确。 |
