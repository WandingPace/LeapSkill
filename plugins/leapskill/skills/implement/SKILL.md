＃ 实施

根据批准的规范、计划或票据集执行范围内的代码更改和彻底验证。

## 核心原则

> **通过垂直跟踪器切片逐步实施，在每个步骤进行验证，并在每个接缝处保持绿色构建。**

---

## 核心不变量

1. **首先批准计划或规范**：切勿在不明确或未经批准的规范上开始广泛实施。
2. **垂直切片进度**：以小型、可测试的跟踪器切片来实现，而不是大规模水平文件编辑。
3. **持续类型检查和测试验证**：每次文件修改后运行本地类型检查和单个测试文件，并在完成之前运行全套。
4. **预提交质量门**：在提交之前通过干净的代码审查（`code-review`）和 lint 检查。
5. **零死亡或推测性代码**：严格编写满足规范所需的代码；避免推测性抽象。

## 分步程序 (TWI)

### 第 1 步：采集规格并验证基线清洁度
- **操作**：阅读规范或票据描述，检查引用的文件，并验证现有的测试套件是否顺利通过。
- **要点**：永远不要开始向损坏或失败的基线添加新功能。
- **为什么**：现有的故障混淆了新更改的回归检测。

### 步骤 2：通过垂直切片 (TDD) 实施
- **操作**：对于每个票证或组件，在公共接缝处编写失败断言，然后实现最小传递逻辑。
- **要点**：保持编辑内容并避免触及不相关的模块。
- **内嵌清单**：
  - [ ] 公共接缝的识别和测试
  - [ ] 类型检查通过且没有错误
  - [ ] 目标测试顺利通过

### 步骤 3：完整的测试套件和质量验证
- **操作**：在整个存储库中运行完整的项目测试套件、类型检查器和 linter。
- **关键点**：零故障、零意外警告、零未格式化文件。
- **为什么**：一个模块的变化可能会巧妙地破坏下游消费者。

### 步骤 4：代码审查和最终提交
- **操作**：使用“代码审查”根据存储库编码标准和原始要求审核 git diff。
- **要点**：编写清晰的、具有价值传达性的提交消息，总结变更。
- **为什么**：持久的提交历史为未来的维护者保留了架构推理。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“在测试任何内容之前，我将立即编辑所有 10 个文件。”* | **垂直跟踪切片：立即验证每个文件/单元。** |大量的多文件编辑使得错误难以隔离和调试。 |
| *“类型检查很慢，我会在最后运行它们。”* | **连续运行快速有针对性的检查。** |及早捕获类型错误可以防止构建有缺陷的数据签名。 |
| *“现有的测试套件之前失败了，所以忽略它。”* | **修改代码之前建立干净的基线。** |未解释的故障隐藏了该功能引入的新回归。 |
| *“跳过代码审查，因为代码运行良好。”* | **根据规范和标准进行强制性差异审查。** |功能代码仍然可能违反存储库约定和安全标准。 |
