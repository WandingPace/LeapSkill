# 模块深化（Deepening）

在考虑依赖关系的前提下，安全地把一组浅模块合并成深模块。这里沿用 [SKILL.md](SKILL.md) 中的术语：**module（模块）**、**interface（接口）**、**seam（接缝）**、**adapter（适配器）**。

## 依赖分类

评估深化候选对象时，先给它的依赖分类。分类决定了深化后的模块如何跨接缝测试。

### 1. 进程内依赖

纯计算、内存状态、无 I/O。这类依赖始终可以深化：直接合并模块，并通过新接口测试，不需要 adapter。

### 2. 本地可替换依赖

指能在本地测试中替代真实依赖的组件，例如用 PGLite 替代 Postgres、用内存文件系统替代磁盘。只要存在这种替身，就可以深化。深化后的模块在测试套件里使用替身运行。接缝是内部接缝，不需要在模块对外接口上暴露 port（端口）。

### 3. 远程但自有（Ports & Adapters）

指跨网络边界但由你自己维护的服务，例如微服务、内部 API。在接缝处定义一个 **port（接口）**。深模块持有业务逻辑；传输方式以 **adapter（适配器）** 的形式注入。测试使用内存 adapter，生产使用 HTTP/gRPC/queue adapter。

推荐表述方式：*“在接缝处定义 port，生产环境实现 HTTP adapter，测试环境实现内存 adapter；这样即使部署上跨网络，业务逻辑仍然集中在一个深模块里。”*

### 4. 真正的外部依赖（Mock）

指你无法控制的第三方服务，例如 Stripe、Twilio。深化后的模块把外部依赖抽象成注入的 port；测试提供 mock adapter。

## 接缝纪律

- **一个 adapter 只是假设中的接缝，两个 adapter 才是真实接缝。** 如果没有充分理由至少存在两个 adapter（通常是生产 + 测试），就不要引入 port。只有一个 adapter 的接缝只是多余的间接层。
- **内部接缝与外部接缝。** 深模块除了接口上的外部接缝，也可以有内部接缝：实现私有、仅供自己的测试使用。不要因为测试要用，就把内部接缝暴露到对外接口上。

## 测试策略：替换，而不是叠加

- 一旦有了面向深化后模块接口的测试，原本针对浅模块的单元测试就成了废料，应删除。
- 在深化后模块的接口上写新测试。**接口就是测试面。**
- 测试只断言通过接口可观察到的结果，不断言内部状态。
- 测试应能在内部重构后继续存在，因为它们描述的是行为而非实现。如果实现变了测试就必须改，说明它测到了接口之外的东西。
