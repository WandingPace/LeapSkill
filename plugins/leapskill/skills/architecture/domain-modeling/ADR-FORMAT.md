# ADR 格式

ADR 保存在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

`docs/adr/` 目录按需创建：只在需要第一个 ADR 时才建立。

## 模板

```md
# {决策的短标题}

{1-3 句话：背景是什么、我们决定什么、为什么。}
```

就是这样。ADR 可以只有一段。它的价值在于记录**做过这个决定**以及**为什么**，而不是把章节填满。

## 可选章节

只有真正有价值时才加这些章节。多数 ADR 用不到。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策可能会被重新讨论时有用
- **Considered Options**（备选方案）：只有值得记住被否决的替代方案时才写
- **Consequences**（后果）：只有存在不明显的下游影响、需要特别指出时才写

## 编号

扫描 `docs/adr/` 中现有编号的最大值，然后加一。

## 什么时候建议写 ADR

以下三点必须同时成立：

1. **难以回退**：将来改变主意的成本很高
2. **缺上下文时会显得奇怪**：未来的读者看到代码会想“他们当时为什么这么写？”
3. **来自真实的权衡**：确实存在不同选项，并且基于具体理由选了其中一个

如果决定容易回退，就不用记录，直接改回去即可。如果并不令人意外，也不会有人想知道原因。如果没有真实的替代方案，那最多就是“我们做了显而易见的事”，没有记录价值。

### 适合记录的决策

- **架构形态。** “我们使用 monorepo。”“写模型采用 event sourcing，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过 domain event 通信，不用同步 HTTP。”
- **有锁定效应的技术选择。** 数据库、消息总线、认证服务、部署目标。不是每个库都要记，只记那些换掉需要花一个季度的。
- **边界与职责范围决策。** “Customer 数据归 Customer 上下文所有，其他上下文只能通过 ID 引用。”明确的“不做什么”和“做什么”一样有价值。
- **有意偏离常规路径。** “我们因为 X 使用手写 SQL，而不是 ORM。”任何合理读者会默认相反做法的决策都算。这类记录能防止下一个工程师把有意设计“修掉”。
- **代码里看不出来的约束。** “因为合规要求，我们不能用 AWS。”“因为合作方 API 合同，响应时间必须低于 200ms。”
- **不明显被否决的备选方案。** 如果你考虑过 GraphQL，却因为一些细微原因选了 REST，就记下来；否则半年后一定有人再提 GraphQL。
