# 拷问式访谈

不断地对思维进行压力测试，揭露隐藏的假设，并将设计空间映射为不断扩展的决策树，直到达成相互理解。

---

## 核心不变量

1. **基于前沿的批量轮次**：在单个编号轮次中一起询问所有当前未被阻塞的问题；决不一一挤牙膏式提问。
2. **强制性具体建议**：每个问题都必须包含明确的推荐答案（`➡️ [推荐]`）以简化决策。
3. **自主事实探索**：在提出问题之前通过背景探索来调查代码库、配置和依赖项；永远不要向用户询问可发现的事实。
4. **严格的拓扑依赖排序**：答案取决于开放决策的问题必须等待未来的轮次；切勿将相关问题混入当前前沿。
5. **前沿耗尽门**：只有当前沿为空并且用户明确确认最终共识时，访谈才会结束。

## 分步程序 (TWI)

### 第 1 步：绘制设计空间和计算前沿
- **行动**：分析用户的意图，识别所有决策节点，并仅选择那些先决条件完全满足的节点。
- **要点**：过滤掉任何需要猜测未解决的同行问题答案的问题。
- **为什么**：同时提出相关问题迫使用户做出推测性的、有条件的答案，从而扰乱上下文。

### 第 2 步：格式化并发送问题轮次
- **行动**：使用标准化 Markdown 问题格式呈现当前前沿：
  ```markdown
❓ **Q1** - **<问题标题>**：<详细问题正文和选项>

➡️ **建议**：<具体建议的答案和技术原理>

  ---

❓ **Q2** - **<问题标题>**：<详细问题正文和选项>

➡️ **建议**：<具体建议的答案和技术原理>
  ```
- **要点**：保持建议固执己见、清晰，并以行业最佳实践为基础。
- **内嵌清单**：
  - [ ] 每个问题都有编号和标题
  - [ ] 为每个问题提供具体建议
  - [ ] 同一轮中不包含相关问题

### 步骤 3：获取答案并推进前沿树
- **行动**：解析用户响应，记录已解决的决策，解锁新可用的下游问题，并生成下一轮。
- **要点**：如果用户响应在代码库中揭示了新的未知，请立即调度后台探索来解决它。
- **为什么**：实时后台发现可以防止将事实负担转嫁给用户。

### 步骤 4：验证对齐和完成
- **行动**：一旦探索了决策树的所有分支并且没有剩余前沿问题，则呈现所有已解决决策的简明综合。
- **要点**：在继续规范或执行之前需要明确的用户确认。
- **为什么**：相互协调保证后续实施阶段的顺利进行，没有摩擦或错误的假设。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“我现在只问一个问题，看看他们怎么说。”* | **一轮问完当前前沿。** |逐题挤牙膏会拖慢节奏，并丢失设计全局结构。 |
| *“让用户自己决定，不要因为我的建议而对他们产生偏见。”* | **每个问题的强制推荐答案。** |具体的建议可以加快审核速度，并为用户提供清晰的反应基准。 |
| *“询问用户配置文件或类型的定义位置。”* | **自主发现环境事实。** |用户访谈专门用于产品和架构决策，而不是存储库搜索。 |
| *“用户给出了一个模糊的答案，但我可以猜出他们的意思。”* | **立即澄清模棱两可的答案。** |在拷问过程中猜测用户意图破坏了压力测试的整个目的。 |
