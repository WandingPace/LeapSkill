# 拷问我

在编写代码之前，进行一次聚焦且持续的苏格拉底式访谈，对计划、架构决策、需求或新生概念进行压力测试。

---

## 核心不变量

1. **不懈的前沿探索**：将设计空间建模为决策树，并在声明对齐之前穷尽前沿。
2. **按轮批量提问**：将问题批量分成结构化前沿轮次，并采用推荐的默认值；切勿用一次性挤牙膏式提问来审问。
3. **自主事实提取**：自主检索代码库、系统和文件事实；永远不要询问用户环境可以揭示什么。
4. **主动假设失效**：主动挑战舒适的假设、规模瓶颈、边缘情况故障模式和隐藏的依赖关系。
5. **不要过早实施**：拒绝编写生产代码或工单，直到待问问题前沿为空且双方同意为止。

```
[ Nascent Idea / Unsettled Decision ] ──► [ Autonomous Codebase Recon ] ──► [ Frontier Question Round ] ──► [ Socratic Refinement ] ──► [ Settled Alignment ]
```

|组件|责任|参考/目标|
|---|---|---|
| **自主侦察** |阅读存储库上下文、ADR、架构 |主要源文件|
| **前沿树** |绘制开放决策节点和先决条件 | `skills/grilling/SKILL.md` |

| **明确对齐** |干净、明确的问题/解决方案契约 |交给“to-spec” |

## 分步程序 (TWI)

### 第 1 步：自主侦察和背景收集
- **行动**：在起草问题之前检查相关的代码库文件、配置、文档和现有的架构决策。
- **关键点**：形成现有约束的基础心理模型，而不询问用户基线事实。
- **为什么**：向用户询问存储库中可用的事实会浪费他们的认知带宽并损害可信度。

### 第 2 步：制定前沿问题轮次
- **行动**：确定先决条件已解决的所有开放决策，并在单个批次中呈现它们并提供明确的建议。
- **要点**：将每个问题的格式设置为“❓ **Q[N]** - **[标题]**:”，其中包含选项和“➡️ [推荐默认值]”。
- **为什么**：提出强有力的建议可以降低决策疲劳，同时迫使用户积极确认或推翻特定选择。
- **内嵌清单**：
  - [ ] 每个问题都针对真正的决定而不是环境事实
  - [ ] 问题是独立的，可以并行回答
  - [ ] 为每个问题提供具体建议
  - [ ] 没有启动执行代码

### 步骤 3：迭代并深化决策树
- **行动**：摄取用户答案，折叠已解析的节点，发现新的下游分支，并发出下一轮前沿。
- **关键点**：探究边缘情况：故障模式、安全边界、迁移路径和不愉快的路径。
- **为什么**：大多数架构失败都发生在最初提案随意掩盖的边界处。

### 步骤 4：验证对齐和闭合
- **行动**：总结统一决策合约并要求用户明确确认。
- **关键点**：确认问题前沿为空，并且存在零个未经检验的假设。
- **为什么**：清晰的对齐可以防止实施过程中代价高昂的重写。

## 反合理化护栏

|诱人的合理化|约束规则|工程原理 |
|---|---|---|
| *“用户的初始提示看起来足够清晰，让我们开始编码。”* | **所有重要计划均强制拷问。** |最初的提示几乎总是隐藏边缘情况的模糊性和冲突的约束。 |
| *“我会在多个来回回合中一一提出问题。”* | **将当前前沿整理成编号轮次。** |单问题乒乓球会造成对话疲劳并破坏上下文。 |
| *“询问用户使用的是哪个数据库模式或库版本。”* | **自主发现环境事实。** |代理必须直接在代码和配置中查找事实，而不是给用户增加负担。 |
| *“同意用户的首选方法，无需进行权衡。”* | **对每个关键设计决策进行压力测试。** |谄媚使得架构错误和扩展瓶颈溜进生产中。 |
