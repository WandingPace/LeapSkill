# UI 原型

在同一路由上生成**几个结构差异明显的 UI 变体**，通过底部浮动条切换。用户在浏览器里翻看变体，选一个（或从各处偷元素），然后丢掉其余。

如果问题关于逻辑/状态而不是外观，这个分支不对。用 [LOGIC.md](LOGIC.md)。

## 什么时候适合这个形态

- “这个页面应该长什么样？”
- “我想在定下来前看几个 dashboard 方案。”
- “设置页换个布局试试。”
- 任何用户本来要在脑子里花一天挑三个模糊 mockup 的场景。

## 两种子形态：强烈优先 A

UI 原型在**贴着真实应用**时更容易判断：真实 header、真实 sidebar、真实数据、真实密度。独立的一次性路由是真空环境，每个变体单独看都还行。只要有合适的现有页面承载变体，默认用 A。只有原型确实没有附近宿主时才用 B。

### 子形态 A：调整现有页面（首选）

路由已存在。变体渲染在**同一路由**上，由 `?variant=` URL search param 控制。现有数据获取、参数和 auth 保持不变，只换渲染。这是默认；没有具体理由就不要偏离。

如果要原型的东西还没有页面，但**天然属于某个页面**（dashboard 新区块、设置页新卡片、现有流程新步骤），仍然是 A。把变体挂进宿主页面。

### 子形态 B：新页面（最后手段）

只有被原型化的东西确实没有可嵌入的现有页面时使用（全新顶层界面，或无法合理嵌入的流程）。

按项目现有路由约定创建**throwaway route**。不要发明新的顶层结构。命名要一眼看出是原型（路径或文件名包含 `prototype`）。同样用 `?variant=` 模式。

选择 B 前先 sanity check：真的没有页面能嵌吗？空路由会掩盖有内容页面会暴露的设计问题。

两种子形态的浮动底栏相同。

## 流程

### 1. 写清问题并确定 N

默认 **3 个变体**。超过 5 个就不是差异明显，而是噪音，所以封顶 5。

把计划写成一排，放在原型位置或文件顶部注释：

> “设置页三个变体，通过 `?variant=` 切换，挂在现有 `/settings` 路由。”

用户在场或不在场时这都有效。

### 2. 生成差异明显的变体

逐个起草。每个变体必须遵守：

- 页面目的和它可访问的数据。
- 项目组件库 / 样式系统（TailwindCSS、shadcn、MUI、plain CSS，什么都行）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构不同**：布局不同、信息层级不同、主 affordance 不同，不只是颜色不同。三个轻微调整的 card grid 不是 UI 原型，是壁纸。如果两个草稿太像，带着“不要用 card grid”的明确约束重做一个。

### 3. 连接它们

在路由上创建一个 switcher 组件：

```tsx
// pseudo-code，按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把现有数据获取放在 switcher 之上；每个变体只替换渲染子树。

子形态 B（新页面）：throwaway route `/prototype/<name>` 挂同一个 switcher。

### 4. 构建浮动 switcher

屏幕底部居中的小型 fixed bar，三部分：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前 key；如果变体导出名称，也显示名称。例如 `B (Sidebar layout)`。
- **右箭头**：切到下一个（循环）。

行为：

- 点击箭头更新 URL search param（用框架 router，例如 Next 的 `router.replace`、React Router 的 `navigate`），让变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 也可切换。`<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截。
- 视觉上和页面明显区隔（例如高对比 pill、轻阴影），让它显然不属于被评估的设计。
- 生产构建隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查，避免误合并把 bar 发给用户。

switcher 放在单个共享组件里，让两个子形态都能复用。位置放在项目共享 UI 的位置。

### 5. 交付

给出 URL（和 `?variant=` key）。用户会自己翻。有价值的反馈通常是**“我要 B 的 header 加 C 的 sidebar”**，那才是他们真正想要的设计。

### 6. 捕获答案并清理

变体胜出后，捕获答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 的方式捕获原型。把赢家折进真实代码，其余移到 throwaway branch，不要留在 main：

- **子形态 A**：把赢家折进现有页面；从 main 删除落选变体和 switcher。
- **子形态 B**：把赢家提升为真实路由；从 main 删除 throwaway route 和 switcher。

完整变体集是一手来源，所以进 throwaway branch 而不是垃圾桶；留在 main 的变体组件和 switcher 很快会腐烂，并困扰下一个读者。

## 反模式

- **变体只差颜色或文案。** 那是 tweak，不是原型。真正的变体应该在结构上意见不同。
- **变体之间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 会毁掉意义。每个变体都应该能推翻布局。
- **把变体接到真实 mutation。** 只读原型没问题。需要变更时指向 stub：问题是“这应该长什么样”，不是“后端能不能用”。
- **把原型直接提升为生产。** 变体代码是在原型约束下写的（无测试、最小错误处理）。折进真实代码时重新好好写。
