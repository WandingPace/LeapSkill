# 任务工件模板

所有标题、说明、结论和表格内容使用中文。轻路径的 spec/plan 与 SDD brief/report 同样适用。替换方括号中的内容；已批准工件中不得残留占位符。代码标识符、API 名、文件路径、命令、日志原文、状态枚举和严重级别可保留原文。

## requirements.md

```markdown
# [任务名称]

## 目标
## 使用者与预期结果
## 成功标准
## 约束
## 范围外
## 已确认决策
## 假设
## 待确认问题
```

每项假设必须包含 Owner 和验证路径。计划进入审批时不得遗留未解决的高影响问题。

### 澄清问题契约

`CLARIFICATION` 阶段，以及需求对抗评审中需要用户决定产品意图时，每个问题都按以下结构表达并记录到 `requirements.md`。面向用户时可省略无内容的小节，但不得省略“影响的数据”“影响的流程”“影响范围”；确实没有影响时明确写“无”。

```markdown
### Q[N]：[一句话说明要决定什么]
- 为什么现在要确认：[说明不确认会阻塞哪项行为、兼容性或计划决策]
- 当前事实：[用易懂语言概括已查明的现状与证据]
- 影响的数据：[具体类/结构/字段/schema/config/asset/存储或“无”；说明新增、修改、删除、迁移及兼容性]
- 影响的流程：[入口 → Owner → 下游结果；说明选择前后流程如何变化]
- 影响范围：[受影响的用户、平台、模式、阶段、版本或存量数据]
- 明确不影响：[容易被误解但实际不受影响的区域]
- 选项 A：[选择后的可观察结果、代价与风险]
- 选项 B：[选择后的可观察结果、代价与风险]
- 推荐：[推荐选项及依据]
- 请确认：[给出直接答复格式，例如“回复 A”或“回复 B，并补充……”。]
- 用户答复：[原文、时间和据此更新的需求/计划位置]
```

写给用户的问题先讲可观察结果，再补充代码标识符；不要只粘贴 review finding、只问“是否接受”，或使用没有解释的内部术语。不同数据结构或不同流程的决策分开提问；只有共同选择、共同生效的事项才合并。单次最多展示三个决策。

面向用户时使用下面的紧凑格式。每项先写结论，再用一两句话解释；代码标识符放在易懂名称之后的括号中。

```markdown
### 需要你决定：[用户能理解的一句话]
[为什么现在必须决定，以及不决定会阻塞什么。]

**会影响**
- 数据：[改哪类数据、是否迁移、旧数据是否兼容；无则写“无”。]
- 流程：[从哪个操作开始，哪个环节变化，用户最终看到什么。]
- 范围：[哪些用户/平台/模式/版本受影响；明确哪些不受影响。]

**可选方案**
- A：[可观察结果]；代价/风险：[一句话]
- B：[可观察结果]；代价/风险：[一句话]

**建议**
推荐 [A/B]，因为 [与需求、风险或兼容性直接相关的理由]。

**请回复**
回复 `A` 或 `B`；如选择需要附加条件，再明确列出需要补充的内容。
```

## research.md

```markdown
# 调研：[任务名称]

## 核心结论
## 当前架构与 Owner
## 执行与数据流
## 接口、存储与兼容性
## 构建与测试入口
## 证据
| 结论 | 证据：路径/符号/行或 URL | 命令 | 可信度 |
|---|---|---|---|
## 矛盾与处理
## 剩余用户决策
```

使用目标 Revision 的证据，明确区分已观察事实与推断。
“剩余用户决策”只列无法通过调研解决的产品意图，并引用 `requirements.md` 中对应的 `Q[N]`；不得把 discoverable 事实包装成用户问题。

## plan.md

### 多阶段计划拆分

复杂或多阶段任务不要把所有实施细节写进 `plan.md`。`plan.md` 只保留总览；每个可独立实施、独立验证的阶段写入 `plan01.md`、`plan02.md` 等阶段文件。

`plan.md` 只包含：

- 版本、状态和阶段文件索引；
- 用大白话表达的底层改造思路；
- 一张端到端高层流程图；
- 阶段顺序和退出条件；
- 全局不变量、范围外和批准记录。

总览不得下沉到具体反射字段、方法名、测试命令或逐文件改动；这些属于阶段文件。

每个 `planNN.md` 必须自足并可独立评审，包含：

- 阶段目标和基础原理；
- 前置条件和已批准输入；
- 精确新增/修改/删除文件；
- 受影响的类、结构、方法、配置、资产和 target；
- 数据结构树与执行/数据流改动；
- 兼容性、迁移、生命周期、线程、失败和回滚；
- 允许写入范围与明确范围外；
- 可直接执行的自动验证、可观测预期和人工门禁；
- 完成证据、回滚点和下一门禁；
- 可选：本阶段有序实施步骤（同一份合同内的顺序，不是独立评审门禁）。

禁止在阶段文件中再拆 `Task N` 或「实施任务」编号列表。已切阶段后，阶段是唯一实施、派发和评审单元。轻路径无阶段计划仍按 `writing-plans` 的 Task 拆分。`status.md` 的阶段台账一行只写一个阶段（`A` / `plan01`），不要写 `A / Task 1`。

旧版本归档为 `plan.v<N>-archive.md`。计划实质变化时，同一轮更新 `status.md`、`review.md` 和 `research.md`，不得留下与当前计划矛盾的旧状态、OPEN finding 或已被覆盖的调研结论。

```markdown
# 实施计划：[任务名称]

## 已批准需求基线
## 架构与数据流
### 改动的数据结构
### 执行流程与数据流
## 公开接口与数据变更
## 阶段 1：[完整结果]
### 目标
### 前置条件
### 文件与符号
### 数据结构改动
### 执行流程与数据流
### 实施流程
（本阶段内有序步骤，不是独立 Task）
### 数据与兼容性
### 失败处理、生命周期与回滚
### 允许写入范围
### 自动验证
### 人工验证
### 完成证据
### 退出门禁
## 阶段 2：...
## 最终集成验证
## 残余风险
## 批准记录
```

不适用的章节填写“无”，不得静默省略。命令必须可直接执行，预期结果必须可观测。

### 引擎执行/数据流标注约定

涉及引擎代码（C++/C#）的 `plan.md`，其“架构与数据流”及每个阶段的“数据结构改动”“执行流程与数据流”章节，统一使用以下标注约定：

- 每个改动的类、结构、函数标注文件名与行号，格式为 `名称 //相对路径:行号`，跳转链接放在代码块外；任务开始后源码行号可能漂移，标注以计划起草时为准。
- 数据结构：只列改动涉及的字段，用 `◆`（必填/必经）与 `◇`（可选/编译期条件存在）作条目前缀；字段标 `NEW`（新增）、`FILL`（填充点）、`DEL`（释放点）等生命周期标记；不重复罗列无关字段。
- 调用堆栈：用 `▶`（必经流程）与 `▷`（条件流程，含运行时 `if` 与编译期 `#if`）作条目前缀；严格按缩进表达调用深度；同命名空间的下一级调用省略 `ClassName::`，跨类/跨命名空间写全；不伪造方法，无需说明的直链可用 `A → B → C` 一行代替。
- 行内数据流用 `→`，子调用用 `↳`，累加用 `⊕`，条件说明用 `※` 紧跟 `//` 之后，不再写 `BRANCH：xxx` 文字注释。
- 改动前后对比：先写“改动前”现状链（可用一行概括），再写“改动后”完整链；重点是控制流和数据流在改动前后的差异，不是全文抄录现有流程。
- 剃刀原则：只保留理解改动所必需的信息；模块只做大的区分；详细逻辑用一句话注释概括。

## review.md

```markdown
# 评审：[任务名称]

## 需求对抗第 [N] 轮
| ID | 严重级别 | 问题与证据 | 主代理处理意见 | 计划变更 | 状态 |
|---|---|---|---|---|---|

## 阶段 [N] 代码评审第 [N] 轮
| ID | 严重级别 | 文件/行 | 行为风险 | 必须修改 | 状态 |
|---|---|---|---|---|---|
```

`P0` 表示灾难性、安全或数据丢失阻塞项；`P1` 表示很可能造成正确性或需求失败的问题；`P2` 表示有实际影响但范围有限的缺陷；`P3` 表示轻微改进。

## status.md

```markdown
# 状态：[任务名称]

- 当前状态：`INTAKE`
- 已批准计划版本：无
- 当前实施阶段：无
  （只写阶段字母或 `planNN`，例如 `A`；不要写 `A / Task 1`）
- 活跃代理：无
- 最近状态转换：[时间与原因]
- 下一项允许操作：[单一操作]

## 阶段台账
| 阶段 | Implementation Agent | Review Agent/轮次 | 自动验证 | 人工门禁 | 结果 |
|---|---|---|---|---|---|

## 审批台账
| 工件/阶段 | Revision/证据 | 用户批准 | 时间 |
|---|---|---|---|

## 阻塞项与残余风险
```

`status.md` 是权威状态记录，不得宣称超出已记录状态和证据的进展。
